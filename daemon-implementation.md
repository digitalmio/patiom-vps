# Patiom Daemon Implementation Plan

This document outlines the complete implementation plan for the Patiom daemon. It serves as the source of truth for building the server-side deployment system.

**Source of truth for product spec:** `README.md` (not `spec.md`)

---

## 1. Configuration Model

All configuration lives in the user's `package.json` under the `patiom` key:

```json
{
  "name": "my-api",
  "scripts": {
    "build": "tsc",
    "start": "node dist/index.js"
  },
  "patiom": {
    "include": ["dist"],
    "domains": ["api.mydomain.com"],
    "patiomRunDomain": true,
    "instances": 2,
    "dbFolder": "db",
    "storageFolder": "storage"
  }
}
```

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `include` | `string[]` | `[]` | Files/directories to bundle in deployment archive |
| `domains` | `string[]` | `[]` | Custom domain names (optional) |
| `patiomRunDomain` | `boolean` | `true` | Auto-assign `{name}.{ip-dashes}.patiom.run` subdomain |
| `instances` | `number` | `1` | Number of processes to run (future: `"maxcpu"`) |
| `dbFolder` | `string` | `"db"` | Name of the database folder (symlinked into each release) |
| `storageFolder` | `string` | `"storage"` | Persistent storage for uploads, cache, etc. (symlinked into each release) |

## 2. Server Layout

### Filesystem Structure

```
/var/lib/patiom/
├── token                    # Auth token (generated by setup.sh)
├── ip                       # Public IP (detected by setup.sh, re-checked on daemon start)
└── apps/
    └── my-api/
        ├── releases/
        │   ├── 1717080000/
        │   │   ├── dist/
        │   │   ├── package.json
        │   │   ├── db -> ../../shared/db/            # symlink to shared db folder
        │   │   └── storage -> ../../shared/storage/   # symlink to shared storage folder
        │   └── 1717087200/
        │       ├── dist/
        │       ├── package.json
        │       ├── db -> ../../shared/db/            # symlink to shared db folder
        │       └── storage -> ../../shared/storage/   # symlink to shared storage folder
        ├── shared/
        │   ├── .env
        │   ├── db/
        │   │   ├── data.db
        │   │   └── cache.db
        │   └── storage/
        │       ├── uploads/
        │       └── cache/
        └── current -> releases/1717087200/
```

### Database Folder

- All SQLite databases live in `shared/<dbFolder>/` (default: `shared/db/`)
- On each deploy, daemon creates a symlink: `releases/<id>/<dbFolder> -> ../../shared/<dbFolder>/`
- User code uses natural paths: `./db/data.db`, `./db/cache.db`
- Folder name is configurable via `patiom.dbFolder` in `package.json`
- Managed via CLI commands: `patiom db list`, `patiom db add <name>`, `patiom db remove <name>`

### Environment Variables (`.env`)

- Secrets and environment variables live in `shared/.env` — never in the archive, never committed
- Stored with `0600` permissions
- Injected into apps via systemd `EnvironmentFile`
- Managed via CLI commands: `patiom env set KEY=VALUE`, `patiom env delete KEY`
- Daemon routes: `POST /env` (set key=value), `DELETE /env/:key` (delete)
- Core module (`core/env.ts`): uses `dotenv` library — `dotenv.parse()` to read, custom serializer to write
- Plaintext (no encryption) — server security is the boundary
- Empty `.env` file created on first deploy if it doesn't exist

### Storage Folder

- General-purpose persistent storage for uploads, generated files, cache, exports, etc.
- All files live in `shared/<storageFolder>/` (default: `shared/storage/`)
- On each deploy, daemon creates a symlink: `releases/<id>/<storageFolder> -> ../../shared/<storageFolder>/`
- User code uses natural paths: `./storage/uploads/avatar.jpg`, `./storage/exports/report.pdf`
- Folder name is configurable via `patiom.storageFolder` in `package.json`
- Auto-created on first deploy (no manual setup needed)
- Survives all deployments — never cleaned up
- **Differentiator over Docker-based PaaS:** no volume mount config required, just works

### Key Paths

- **PATIOM_ROOT:** `/var/lib/patiom/`
- **Apps directory:** `/var/lib/patiom/apps/`
- **Token file:** `/var/lib/patiom/token`
- **IP file:** `/var/lib/patiom/ip`
- **ACME registry:** `/var/lib/patiom/acme_registry`

## 3. Clustering: systemd Template Units

Each app uses systemd template units with `%i` for port injection:

```ini
[Unit]
Description=Patiom App: my-api (instance %i)
After=network.target

[Service]
Type=exec
WorkingDirectory=/var/lib/patiom/apps/my-api/current
ExecStart=/usr/bin/node dist/index.js
Restart=always
Environment="PORT=%i"
EnvironmentFile=/var/lib/patiom/apps/my-api/shared/.env

DynamicUser=yes
ProtectSystem=strict
ProtectHome=yes
ReadWritePaths=/var/lib/patiom/apps/my-api

[Install]
WantedBy=multi-user.target
```

### Deployment with Instances

For `instances: 3`:
```bash
systemctl enable --now my-api@50001 my-api@50002 my-api@50003
```

Ports are allocated as a contiguous block from the range `50000-51000`.

### Instance Count Changes

If `instances` changes on redeploy:
1. Stop old instances
2. Allocate new port block
3. Enable + start new instances
4. Update rpxy config

## 4. rpxy Configuration

### Global ACME Config (set once during setup.sh)

The ACME relay choice is made during server setup and written to rpxy's config.toml. The daemon does not need to manage this — rpxy handles it.

**Option 1: Patiom ACME relay (default)**

All certificate requests pass through `acme.patiom.dev`. `*.patiom.run` domains use ZeroSSL via Patiom's account. Custom domains are forwarded to Let's Encrypt. Required for `patiom.run` domains.

```toml
listen_port = 80
listen_port_tls = 443

[experimental.acme]
dir_url = "https://acme.patiom.dev/directory"
email = "acme@patiom.dev"
registry_path = "/var/lib/patiom/acme_registry"
```

**Option 2: Direct Let's Encrypt**

User provides their own email. No `patiom.run` subdomains. Set via `setup.sh --no-acme-proxy --email you@example.com`.

```toml
listen_port = 80
listen_port_tls = 443

[experimental.acme]
dir_url = "https://acme-v02.api.letsencrypt.org/directory"
email = "you@example.com"
registry_path = "/var/lib/patiom/acme_registry"
```

### Per-App Config (with load balancing)

```toml
[apps.my-api]
server_name = "my-api.1-2-3-4.patiom.run"
tls = { https_redirection = true, acme = true }

[[apps.my-api.reverse_proxy]]
upstream = [
  { location = "127.0.0.1:50001" },
  { location = "127.0.0.1:50002" },
  { location = "127.0.0.1:50003" }
]
load_balance = "round_robin"
```

### Custom Domains

If user has `"domains": ["api.mydomain.com"]`, create a separate rpxy app block:

```toml
[apps.my-api-custom]
server_name = "api.mydomain.com"
tls = { https_redirection = true, acme = true }

[[apps.my-api-custom.reverse_proxy]]
upstream = [
  { location = "127.0.0.1:50001" },
  { location = "127.0.0.1:50002" },
  { location = "127.0.0.1:50003" }
]
load_balance = "round_robin"
```

rpxy hot-reloads config changes — no restart needed.

## 5. Deploy Flow

### `POST /deploy` Handler

1. **Auth** → validate Bearer token from `/var/lib/patiom/token`
2. **Parse multipart** → zip blob + app name + config JSON (domains, instances, patiomRunDomain, dbFolder, storageFolder)
3. **Create release** → `/var/lib/patiom/apps/<name>/releases/<timestamp>/`
4. **Extract zip** → into release directory
5. **Create db symlink** → `releases/<timestamp>/<dbFolder> -> ../../shared/<dbFolder>/` (create `shared/<dbFolder>/` if it doesn't exist)
6. **Create storage symlink** → `releases/<timestamp>/<storageFolder> -> ../../shared/<storageFolder>/` (create `shared/<storageFolder>/` if it doesn't exist)
7. **Install deps** → `pnpm install --prod` (stream output to CLI)
8. **Allocate ports** → scan existing systemd units, find free contiguous block
9. **Swap symlink** → `current -> releases/<timestamp>/`
10. **Write systemd unit** → template unit file with app name
11. **Manage instances** → stop old (if any), enable + start new instances
12. **Build domain list** → custom domains + patiom.run domain
13. **Update rpxy config** → add/update app blocks with all domains, load-balance upstreams
14. **Stream result** → domains, ports, status back to CLI

## 6. IP Detection

### setup.sh

```bash
curl -s https://api.ipify.org > /var/lib/patiom/ip
```

### Daemon

- Re-checks IP on startup
- Updates `/var/lib/patiom/ip` if changed
- Logs warning if IP changed (user may need to update DNS for custom domains)

### patiom.run Domain Construction

```typescript
const ip = "1.2.3.4";
const ipDashes = ip.replace(/\./g, "-"); // "1-2-3-4"
const domain = `${appName}.${ipDashes}.patiom.run`;
```

Uses sslip.io-style wildcard DNS (already configured).

## 7. Authentication

### Token Generation (setup.sh)

```bash
openssl rand -hex 16 > /var/lib/patiom/token
chmod 600 /var/lib/patiom/token
```

### Daemon

- Reads token from `/var/lib/patiom/token` on startup
- All routes behind Bearer token middleware
- Validates `Authorization: Bearer <token>` header

### CLI

- Token stored in `~/.patiom/config.json`
- Sent as Bearer token on all requests

## 8. Turso Embedded Replicas

### How it works

Turso embedded replicas work out-of-the-box with Patiom. No daemon changes needed.

**The flow:**
1. User creates a Turso database at [turso.io](https://turso.io)
2. Gets an auth token (stored in `.env`)
3. Uses libSQL client with embedded replica config
4. The `.db` file lives in `shared/db/` like any other SQLite file
5. Sync happens automatically via the libSQL client library

```typescript
import { createClient } from "@libsql/client";

const db = createClient({
  url: "file:./db/data.db",              // local SQLite file
  syncUrl: "libsql://mydb.turso.io",     // remote Turso endpoint
  syncInterval: 60,                      // sync every 60 seconds
  authToken: process.env.TURSO_TOKEN,    // from .env
});

// Normal queries work on local file (fast reads/writes)
await db.execute("SELECT * FROM users");

// Explicit sync (or automatic via syncInterval)
await db.sync();
```

### Key points

- **Sync is in the client library, not the file.** The `.db` file itself is just SQLite. The libSQL client handles pushing local changes and pulling remote changes.
- **Works with our design.** The file lives in `shared/db/data.db`, symlinked into each release. The daemon doesn't need to know about Turso.
- **Turso API keys never touch the server.** The auth token goes in `.env` (already secure, `0600` permissions, injected via `EnvironmentFile`).
- **SyncInterval can be 0.** If set to 0, sync only happens on explicit `db.sync()` calls. Useful for request-response patterns.

### Patiom's role

**Option A (v1):** User manages everything. We document the pattern.
- User creates Turso DB, gets token, adds to `.env`
- User code uses libSQL client
- No daemon changes needed
- Just works

**Option C (maybe future):** Documentation + helpers.
- `patiom turso setup` helper command (creates `.env` entry, installs `@libsql/client`)
- Documentation with example code
- But user still manages their own Turso account

**Option B (never):** Patiom integrates Turso directly.
- Would require storing Turso API keys on the server
- Security concerns, maintenance burden
- Not happening

### Differentiator

Turso embedded replicas + Patiom's `shared/db/` = instant edge-replicated SQLite without Docker, without config files, without vendor lock-in to a PaaS. The user owns their server, their data, and their sync logic.

## 11. Decisions Made

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Port range | `50000-51000` | 1000 ports, plenty of room for many apps x instances |
| Release cleanup | v2 | Keep all releases for now, add cleanup later |
| Script detection | Discuss later | `patiom` vs `start` script logic needs more thought |
| Clustering model | systemd template units (`@N`) | Each instance independently restartable, simple |
| Instance count config | `number` in `package.json` | Simple for v1, future: `"maxcpu"` |
| patiom.run domain | On by default | Good for quick testing, opt-out via `patiomRunDomain: false` |
| DNS provider | sslip.io | Wildcard DNS already configured, no setup needed |
| Database management | Folder-based with symlink | All `.db` files in `shared/<dbFolder>/`, symlinked into each release. One symlink per release, not per file. Configurable folder name via `patiom.dbFolder` |
| Storage folder | `storage` by default, symlinked into releases | Persistent storage for uploads, cache, generated files. Survives deployments. Differentiator over Docker PaaS (no volume mount config needed). Configurable via `patiom.storageFolder` |
| Environment variables | `.env` in `shared/`, CLI-managed (`set`/`delete`), `dotenv` library + custom serializer | Secrets never in archive, never committed. Stored with `0600` perms, injected via systemd `EnvironmentFile`. Managed via `patiom env set KEY=VALUE` / `patiom env delete KEY`. Plaintext (no encryption) — server security is the boundary. No list command — values are secret. |
| Turso embedded replicas | User-managed (Option A) + docs (Option C) | Turso works out-of-the-box via libSQL client. Files are just SQLite in `shared/db/`. No daemon changes needed. Document the setup pattern. |
| Daemon database | None | Filesystem-first, inspectable with `ls` |
| ACME relay | `https://acme.patiom.dev/directory` (ZeroSSL) by default, opt-out to Let's Encrypt | Already hosted and working. User chooses during setup.sh. If they opt out, no patiom.run domains. |

## 12. Open Questions (for later)

1. **Script detection:** Should daemon read `scripts.patiom || scripts.start` from uploaded `package.json`? How to handle different package managers (pnpm vs npm vs yarn)?

2. **Health checks:** Should daemon health-check each instance after deploy? What endpoint? What if it fails?

3. **Rollback:** `patiom rollback` command — swap symlink to previous release, restart instances. When to implement?

4. **Logs:** Should daemon provide `patiom logs` endpoint that streams `journalctl` output?

5. **Scaling:** When to add `"maxcpu"` support for `instances`? How to detect CPU count?

6. **Project root detection:** Users may run `patiom deploy` from subdirectories. Need `find-up` to walk up and find the nearest `package.json` with a `patiom` key, rather than relying on `process.cwd()`.

7. **Staging deploys:** Two approaches discussed — (A) multi-server config with separate prod/staging servers and isolated data, (B) deploy-without-publish on the same server (Fly.io style). Open questions:
   - Data isolation: should staging share db/storage with live, or be fully isolated?
   - Cleanup: manual `patiom staging remove`, auto-expire, or both?
   - Domains: `{name}-{nanoid}.{ip}.patiom.run` — needs more certs per staging deploy, or wildcard cert for `*.patiom.run`
   - Promotion: `patiom promote <release-id>` to swap staging to live

## 14. Security Considerations

- **Auth token:** 32-char hex, stored with `0600` permissions
- **DynamicUser:** Each app runs as ephemeral, unprivileged user
- **Sandboxing:** `ProtectSystem=strict`, `ProtectHome=yes`, `ReadWritePaths` locked to app dir
- **Secrets:** `.env` stored in `shared/` with `0600` permissions, injected via `EnvironmentFile`
- **ACME:** Certificates managed by rpxy, stored in `/var/lib/patiom/acme_registry`
